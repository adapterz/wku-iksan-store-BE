# 상품 목록 캐시 세대 분리

관련: [#138 보완 목록 9번](https://github.com/adapterz/wku-iksan-store-BE/issues/138#issuecomment-5793343420)

## 해결 범위

기존에는 상품 변경 후 `products:list:*`를 삭제해도, 변경 전에 시작된 DB 조회가 늦게 끝나 같은 키에 이전 값을 다시 저장할 수 있었다. 이후 요청도 최대 300초 동안 이전 값을 재사용하는 경합을 보완한다.

- 구현 위치: `controllers/productsController.js` 내부. 새 런타임 모듈·패키지는 추가하지 않는다.
- 대상: `GET /api/products`의 상품 목록·검색·카테고리/브랜드 필터 캐시.
- FE, API 요청/응답, SQL/ERD, 환경변수 변경 없음. DB 마이그레이션 불필요.
- 랭킹·인기 검색어의 프로세스 메모리 캐시는 변경하지 않는다.

## 처리 방식

| 키 | 역할 | 만료 |
| --- | --- | --- |
| `products:list-cache:v2:generation` | 모든 서버가 공유하는 현재 세대 UUID | 없음 |
| `products:list-cache:v2:<generation>:<JSON 필터 배열>` | 해당 세대의 상품 목록 | 저장 후 300초 |

1. DB 조회 전에 Redis에서 현재 세대를 읽는다.
2. 세대가 없으면 새 UUID를 `SET ... NX`로 초기화한다. 동시 초기화에서 실패한 요청은 공유된 값을 다시 읽는다. 끝내 세대를 얻지 못하면 캐시를 사용하지 않는다.
3. 조회와 저장 모두 처음 읽은 세대의 데이터 키를 사용한다. 필터 키는 기존 JSON 배열 구분 방식을 유지한다.
4. 상품 등록·수정·상태 변경, 카테고리명 수정, 찜 추가·삭제의 기존 무효화 호출이 DB 변경 완료 후 세대를 새 UUID로 교체한다.
5. 이전 조회의 늦은 저장은 과거 세대에만 남는다. 이후 새 세대를 읽은 요청은 해당 값을 사용하지 않는다. 과거 데이터는 TTL로 정리한다.

무효화는 전체 키 검색/삭제 대신 세대 키 하나를 갱신한다. 캐시 적중 조회에는 기존보다 Redis GET이 한 번 추가된다. 초기화 시에만 NX 및 필요 시 재조회가 추가된다. UUID를 사용하므로 세대 키만 eviction 등으로 없어져도 남아 있는 과거 데이터의 세대 번호를 재사용하지 않는다.

## 장애와 보장 경계

- 세대/데이터 조회 오류: DB로 폴백하고 해당 요청은 캐시 저장도 생략한다.
- 데이터 저장 오류: DB 조회 성공 응답은 유지한다.
- 무효화 오류: 기존과 같이 로그를 남기며 이미 성공한 DB 변경을 실패로 바꾸지 않는다. 이때는 최신 캐시 반영을 보장하지 못한다.
- 변경 전에 시작된 요청 자체에 이전 값이 반환될 수 있다. 이미 진행 중인 HTTP 응답까지 취소하거나 선형화하는 설계는 아니다.
- DB 커밋과 Redis 세대 교체는 하나의 트랜잭션이 아니다. 그 사이 프로세스 종료·Redis 장애, Redis 복제/복구로 인한 쓰기 유실까지 해결하지 않는다.
- 과거 세대 데이터가 잠시 함께 남으므로 메모리 사용량이 늘 수 있다. TTL은 지연된 저장이 실제 완료된 시점부터 300초다.

## 배포 시 참고

- 새 키 공간이므로 처음에는 캐시 미스로 DB를 조회한다. 기존 키는 읽지 않으며 기존 TTL로 만료된다. Redis 전체 삭제는 필요 없다.
- **구버전·신버전이 동시에 트래픽을 받는 동안에는 캐시 일관성을 보장하지 않는다. 짧은 혼용 구간도 예외가 아니다.** 구버전의 `products:list:*` 삭제는 신버전 세대에 전달되지 않고, 신버전 세대 교체도 구버전 키를 지우지 않는다.
- 저장소의 `docker-compose.yml`은 BE 서비스 하나를 고정 포트 `4000:4000`에 연결하고, `deploy.sh`는 `docker compose up -d`로 갱신한다. Nginx도 단일 BE 주소를 참조한다. 이는 저장소 기준이며 실제 운영 구성이나 구버전 요청 종료까지 검증했다는 의미는 아니다.
- 다중 서버·롤링·블루그린 전환을 도입한다면 먼저 호환 무효화 또는 혼용 구간의 캐시 우회 정책을 별도 설계한다. 문서 주의사항만으로 자동 차단/감지가 되는 것은 아니다.
- 두 버전이 혼용된 경우, 구버전 인스턴스와 그 진행 중 요청이 모두 종료된 뒤 배포 담당자가 신버전 캐시 세대의 무효화 또는 남은 캐시 TTL 경과를 확인한다. **전체 서버를 신버전으로 바꾸는 것만으로 혼용 중 남은 캐시가 즉시 정리되지는 않는다.** 이후 승인된 검증용 상품의 변경이 목록·검색·필터에 반영되는지 확인한다.
- 롤백 시에는 신버전의 요청 종료와 남아 있는 구버전 목록 캐시의 무효화 또는 TTL 경과를 확인한다. TTL은 각 데이터의 마지막 저장 시점부터 300초이며, 서버 전환 시작 시점부터 계산하지 않는다. 확인 없이 Redis 전체를 삭제하지 않는다.
- 배포 시 빠른 확인 목록은 [README의 상품 목록 캐시 전환 확인](../../README.md#상품-목록-캐시-전환-확인-pr-142)에 둔다. 운영 쓰기·대상 캐시 무효화는 배포 담당자와 범위를 확인한 뒤 수행하며, 이 문서는 운영 Redis 조작이나 배포를 자동으로 수행하라는 지시가 아니다.
