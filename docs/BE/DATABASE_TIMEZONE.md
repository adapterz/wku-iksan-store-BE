# DB 날짜 변환 기준 — 이슈 #147

## 변경 내용

- DB의 `DATETIME`은 한국 시간(KST)으로 저장하고, `db/pool.js`의 `timezone: '+09:00'`으로 읽기·쓰기 기준을 고정한다.
- API는 기존처럼 ISO 8601 UTC 문자열(`Z`)을 반환한다. 새 API·응답 필드·스키마 변경은 없다.
- 예: DB `2026-09-22 21:14:48` → API `2026-09-22T12:14:48.000Z` → 한국 화면 `9월 22일 21:14:48`.
- 기존 UTC 컨테이너에서는 같은 값을 `21:14:48Z`로 해석해 한국 화면에서 다음 날로 표시할 수 있었다.
- FE에서 일괄적으로 9시간을 빼거나, 이미 KST인 DB 날짜를 일괄 수정하지 않는다.

**전제: DB 세션의 `NOW()` / `CURRENT_TIMESTAMP`도 KST여야 한다.** mysql2의 `timezone`은 날짜 변환 옵션이며 MySQL 세션 설정이나 Docker의 `TZ`를 변경하지 않는다. DB 세션이 UTC인 환경에는 이 변경을 그대로 배포하면 안 된다. 로컬 DB도 같은 저장 기준으로 준비한다.

## 배포 전 필수 확인: 기존 제재 종료 시각

`created_at`, 선물의 `used_at` 등은 SQL `CURRENT_TIMESTAMP`로 생성한다. 반면 `user_sanctions.ends_at`은 JS `Date`를 드라이버에 전달한다. 기존 UTC 프로세스 + 기본 mysql2 설정에서 작성한 `ends_at`은 **UTC 숫자로 저장됐을 수 있다.** 이를 새 드라이버가 KST로 읽으면 제재가 9시간 먼저 만료된다.

`DATETIME` 자체에는 시간대나 작성 버전 정보가 없다. `created_at`과의 차이만으로 모든 행의 저장 기준을 확정할 수 없고, 관리자 직접 수정 등으로 혼재할 수도 있다. 이 코드 수정은 기존 데이터를 자동 판별·보정하지 않는다.

### Bio와 확인할 항목

1. 실제 BE 접속 세션에서 아래 조회로 KST인지 확인한다. `SYSTEM`이라는 문자열만으로 판단하지 말고 실제 오프셋도 본다.
   ```sql
   SELECT @@session.time_zone, @@system_time_zone,
          NOW(), UTC_TIMESTAMP(),
          TIMESTAMPDIFF(MINUTE, UTC_TIMESTAMP(), NOW()) AS offset_minutes;
   -- 기대: offset_minutes = 540
   ```
2. 기존 `ends_at IS NOT NULL` 행의 ID·값·상태를 백업하고, 기존 실행 환경/요청 기록과 대조해 UTC로 작성된 대상이 있는지 확인한다. 활성 제재뿐 아니라 만료·해제된 이력도 표시 시간이 달라질 수 있다.
   ```sql
   SELECT id, user_id, type, status, ends_at, created_at
   FROM user_sanctions WHERE ends_at IS NOT NULL ORDER BY id;
   ```
3. 해당 행이 없거나 모두 KST임이 확인되면 보정 SQL은 불필요하다. UTC로 저장된 행은 **확인된 ID와 기존 값으로 한정**해 KST로 보정(+9시간)할 계획을 별도로 검토한다. 불명확한 데이터가 남으면 먼저 확인하고 배포를 보류한다. 전체 날짜/전체 행 일괄 보정은 금지한다.
4. 보정이 필요하면 쓰기를 중단하고 구버전 요청까지 종료 → 백업·대상 값 재확인 → 합의된 보정 1회 → 새 버전 전환 → 검증 후 쓰기 재개 순서로 진행한다. 구버전과 신버전이 동시에 날짜를 기록하지 않도록 한다.
5. 선물 사용일 및 활성 제재의 종료 시각·만료 판단·대시보드 수를 확인한다. 롤백 시에는 코드만 되돌리지 않고 보정 이력과 새 버전이 작성한 `ends_at`까지 대조한 데이터 복원 계획이 필요하다. 무조건 -9시간을 실행하지 않는다.

이 문서는 점검·전환 계획이다. 운영 데이터 확인, 보정, 배포가 완료됐다는 의미가 아니다. 이번 변경에 자동 실행 마이그레이션은 포함하지 않는다.

## 로컬 검증

KST 세션으로 설정한 **격리된 로컬 MySQL 8**에서 실행한다. 기존 서비스 DB 이름은 사용하지 않고 임시 DB를 생성·삭제한다. 테스트는 서버 전역 시간대 설정을 변경하지 않는다.

```powershell
$env:TIMEZONE_DB_TEST = '1'
$env:DB_HOST = '127.0.0.1'
$env:DB_PORT = '<격리된 로컬 MySQL 포트>'
$env:DB_USER = '<테스트 DB 생성·삭제 가능한 로컬 계정>'
$env:DB_PASSWORD = '<로컬 비밀번호>'
npm run test:timezone:db
npm test -- --runInBand
```

테스트가 각각 `TZ=UTC`, `TZ=Asia/Seoul` 자식 프로세스를 실행해 다음을 확인한다.

- 이전 UTC 해석 문제 재현, 수정 후 DATETIME 조회(query/execute), 자정·15시 경계·윤년·NULL
- 실제 선물 목록/상세/사용 처리 HTTP 응답, DB 사용·알림 시각, 원본 KST 데이터 유지
- 실제 제재 모델의 Date 저장·복원, 활성/만료 판단, 관리자 집계, 경고의 NULL 종료 시각
- UTC로 저장한 과거 제재를 흉내 낸 **테스트 데이터만** 한정 보정해 종료 시각 복원 확인

인증은 테스트용 세션을 주입하며 Redis는 격리한다. 운영 환경, 실제 브라우저 화면, 운영 데이터 보정 검증을 대신하지 않는다.
