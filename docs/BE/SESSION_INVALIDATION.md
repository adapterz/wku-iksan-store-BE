# 비밀번호 변경 시 기존 로그인 무효화 (#122)

## 구현 정책

- Aon의 2026-09-15 코멘트에 따라 **현재 기기를 포함한 모든 기존 로그인**을 무효화한다.
- `users.auth_version`은 INT UNSIGNED, 기본 1, 유효 범위 1~4294967295. 상한에서는 변경을 실패시키며 1로 되돌리지 않는다.
- 로그인 시 비밀번호 검증에 사용한 회원 스냅샷의 버전을 서버 세션 `authVersion`에 저장한다. 클라이언트 입력을 사용하거나 응답으로 노출하지 않는다.
- 비밀번호 변경은 `WHERE id = ? AND auth_version = ?` 조건부 UPDATE로 비밀번호와 버전을 함께 갱신한다. 동시 요청은 하나만 성공한다.
- `requireLogin`은 매 요청 DB의 최소 필드(id/auth_version)를 읽어 비교한다. 누락/불일치/탈퇴는 401, DB 조회 장애는 500. 실패한 요청은 실제 기능으로 넘어가지 않는다.
- 인증 검사를 이미 통과한 진행 중 요청을 소급 취소하지 않는다. 구 비밀번호 로그인 검증과 변경이 경합하면 로그인 응답이 200이어도 그 세션은 구 버전이므로 다음 보호 요청에서 거부된다.
- 다른 기기 화면을 즉시 변경하거나 이미 표시한 데이터를 원격 삭제하지 않는다. 메모리 세션 저장소, maxAge, 탭 동기화, FE는 변경하지 않는다.

## API 계약 (신규 엔드포인트 없음)

| API | 변경 사항 |
| --- | --- |
| POST /api/auth/login | 기존 응답 유지. 세션에 authVersion 저장 |
| PATCH /api/users/me/password | 기존 200 PASSWORD_UPDATE_SUCCESS 유지. 현재 세션/쿠키 정리, 모든 구 버전 차단 |
| 동시 비밀번호 변경 | 인증 재검증에서 먼저 발견하면 401 UNAUTHORIZED, 조건부 UPDATE 경합이면 409 PASSWORD_CHANGE_CONFLICT |
| GET /api/auth/me 및 모든 로그인 필수 API | 무효 세션은 401 UNAUTHORIZED, 버전 DB 조회 장애는 500 |
| POST /api/auth/logout | 버전/회원 DB 검사 제외. 정상·구버전·버전 누락·없는 세션·반복 요청도 200 LOGOUT_SUCCESS |

실제 로그아웃 저장소 삭제 오류는 쿠키 제거를 시도하고 500을 반환한다. 반면 비밀번호 변경 후 정리 오류는 DB 변경 성공을 실패로 오인시키지 않도록 200을 유지한다. 남은 세션도 DB 버전 불일치로 차단된다. 성공 응답이 유실돼도 기존 비밀번호/세션이 복구되지 않는다.

FE는 기존 비밀번호 변경 성공 안내와 이후 보호 API의 401 처리를 사용한다. 즉시 재로그인 화면 전환은 이번 구현 범위가 아니다. 다른 로그인 필수 라우트에서 로그아웃 예외를 재사용하지 않는다.

### 후속 보완 — FE 오류 안내

현재 FE에는 `409 PASSWORD_CHANGE_CONFLICT`의 전용 문구가 없어, BE가 재로그인 안내 message를 보내더라도 화면에는 일반 오류 문구가 표시된다. 동시 비밀번호 변경으로 인증 정보가 달라졌음을 알리고 재로그인을 안내하는 문구 보완은 이번 BE 구현 범위에서 제외하고 후속 작업으로 남긴다. 기존 세션의 보호 API 접근 차단은 정상 동작한다.

## 배포 / 마이그레이션

1. Bio와 운영 적용 일정을 조율한다. 이 문서나 로컬 구현은 운영 실행 승인이 아니다.
2. 백업 후 모든 구 BE 프로세스를 중지하고 진행 중 요청 종료를 확인한다.
3. `SHOW COLUMNS FROM users LIKE 'auth_version'`으로 존재 여부를 확인한다. 이미 적용됐으면 파일을 다시 실행하거나 버전을 초기화하지 않는다.
4. `db/migrate_user_auth_version.sql` 실행. 기존 회원은 기본값 1, 비밀번호/다른 도메인 데이터는 유지한다. ALTER TABLE은 자동 커밋된다.
5. 스키마·유효 범위를 검증한 뒤 신규 BE를 배포한다. 버전이 없는 기존 세션은 재로그인이 필요하다.
6. 새 회원 기본값, 두 기기 로그인/비밀번호 변경/구 세션 401/새 비밀번호 로그인/반복 로그아웃을 확인한다.

롤백 시 컬럼은 삭제하지 않는다. 구버전 코드는 버전을 검사하지 않으므로 보안 보장이 사라진다. 코드 복구가 필요하면 프로세스/세션 정리와 차단 정책을 담당자와 먼저 결정해야 한다. 구·신 버전 서버를 혼용하지 않는다.

## 검증

- `npm test -- --runInBand`: 기존 라우터 fixture는 정상 버전 1 및 인증 조회 mock을 제공한다. 인증 검사를 생략하지 않는다.
- `archive/tests/integration/sessionInvalidation.test.js`: 실제 Express/session/쿠키/bcrypt/라우터, DB만 모의. 다중 기기, 경합, 구 세션, DB/저장소 실패, 보호 경로 차단을 검증한다.
- `archive/tests/models/userAuthVersion.test.js`: 최소 컬럼 조회, 원자적 조건부 SQL, 상한/충돌 검증.
- `npm run test:session:db -- <로컬 DB 전용 env 파일>`: 임의 이름의 테스트 DB만 생성/삭제하는 실제 MySQL 검증. 운영 호스트/DB는 사용하지 않는다.
- 로컬 자동 테스트와 실제 MySQL/FE 브라우저/운영 검증은 구분해서 보고한다. FE 샘플의 `/__preview/login` 같은 테스트 전용 세션 생성기에는 별도로 버전 fixture를 적용해야 한다.

- 분리된 임시 MySQL 8.0.46: 실제 마이그레이션, 기존 비밀번호 보존, 새 회원 기본값, 다중 기기 로그인 무효화, 실제 동시 UPDATE 등 16개 검사 통과.
- 기존 장바구니 MySQL 검사 54개, 리뷰 MySQL 검사 74개 및 선물 도착 알림 DB 회귀 검사 통과. 테스트 전용 세션 fixture에도 정상 버전을 지정했다.
- 최신 FE 코드를 최소 DOM/응답 모형에서 실행해 비밀번호 변경 성공 안내와 이후 401 로그인 이동을 확인했다. 409/429는 일반 오류 문구로 표시되어 안내 보완을 후속 작업으로 남긴다. 실제 브라우저 E2E 검증은 아니다.
- 테스트 DB는 검사 후 삭제했고 임시 MySQL 인스턴스도 종료했다. 운영 DB/Redis/서비스는 사용하거나 변경하지 않았다.
- FE 브라우저 및 실제 Nginx 경유 운영 검증은 실행하지 않았다. 배포 전 마이그레이션 일정과 재로그인 영향을 별도로 확인해야 한다.
