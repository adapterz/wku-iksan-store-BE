# 찜 목록 관심 수 — #138 보완 6번

관련: [보완 목록 6번](https://github.com/adapterz/wku-iksan-store-BE/issues/138#issuecomment-5793343420)

## API 응답 추가 명세

기존 `GET /api/wishlists`에 아래 필드를 추가한다. 로그인 필요 조건과 나머지 응답은 유지한다.

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| `data[].product.wishlistCount` | number (정수) | 조회 시점 해당 상품의 전체 찜 개수 |

아래는 응답의 상품 객체 일부다.

```json
{
  "id": 3,
  "name": "커피",
  "status": "active",
  "wishlistCount": 12
}
```

- 목록은 세션 사용자 본인의 찜 상품만 최신 등록순으로 반환한다.
- 관심 수는 본인을 포함한 전체 회원의 찜 개수이며 본인의 목록 길이가 아니다. 회원·상품 UNIQUE 제약으로 중복 찜은 저장되지 않는다.
- 다른 사용자의 ID·닉네임은 추가하지 않는다. 빈 목록은 기존 `data: []`를 유지한다.
- 집계는 `Number()`로 정규화해 FE에서 숫자 덧셈이 문자열 연결로 바뀌지 않게 한다.
- 상품 상태·등록/삭제 응답·캐시 무효화는 변경하지 않는다.

## 조회·FE 연결 방식

기존 목록 SQL에 상품 ID 조건의 `COUNT(*)` 서브쿼리를 추가한다. 바깥 `w.user_id = ?`는 목록 소유자를 제한하고, 안쪽 `all_w.product_id = p.id`는 전체 회원의 찜을 집계한다. 목록 행이 늘어나지 않아 기존 정렬을 유지한다.

상품마다 별도 HTTP/DB 요청을 보내지 않고 **목록 조회 쿼리 한 번**으로 처리한다. 다만 SQL 내부 집계 비용까지 일정해지는 것은 아니다. 기존 상품 외래 키용 인덱스 활용을 전제로 하며, 실제 DB의 `SHOW INDEX FROM wishlists` 및 실제 조회 SQL의 `EXPLAIN` 확인은 남아 있다.

기존 FE `wishlist.js`는 `product`를 공통 카드 함수로 그대로 전달한다. `component.js`는 `wishlistCount`가 있으면 `관심 N`과 `data-count`·`data-has-count`를 설정하므로 FE 제품 코드 변경 없이 연결된다. 찜 해제 시 카드 제거는 기존 흐름을 유지한다.

홈·랭킹은 캐시가 있어 조회 시점에 따라 수치가 잠시 다를 수 있다. 이번 작업은 모든 화면·여러 탭의 실시간 동기화를 보장하는 변경이 아니다.

## 변경 경계

BE 조회·응답·테스트·명세 문서만 변경한다. **추가 API, FE 제품 코드, ERD/DB 구조, 환경변수, 마이그레이션 변경은 없다.** Wiki는 이 브랜치에 포함되지 않으며 본 문서가 응답 추가 명세다.

### 실제 DB·브라우저 후속 확인

격리된 로컬 테스트 DB에서만 다음을 확인한다.

1. A·B가 X를 찜하고 A만 Y를 찜한 경우: A 목록 X·Y의 집계는 2·1, B 목록 X의 집계는 2. 다른 회원만 찜한 상품은 목록에 섞이지 않아야 한다.
2. B가 X를 해제한 뒤 A의 X는 1, B 목록은 비어 있는지 확인한다.
3. 정렬·상품 상태·비로그인 401·실패 응답이 유지되는지 확인한다.
4. FE 찜 화면에서 응답 수치와 표시가 일치하고 해제 시 카드가 제거되는지 확인한다.
5. 충분한 테스트 데이터를 넣고 실행 계획에서 사용자·상품 조건의 인덱스 사용을 확인한다. 조회 왕복이 한 번이라는 이유만으로 성능 검증 완료로 보지 않는다.
